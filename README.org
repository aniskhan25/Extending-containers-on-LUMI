#+TITLE: Extending Containers on LUMI — TransformerEngine
#+AUTHOR: Anis Rahman
#+OPTIONS: toc:nil
#+OPTIONS: num:nil

This guide builds a container that restores fused attention in the LUMI AI Factory
=plus= image on MI250x.

It is a workaround, not a fix: the defect is upstream in the =plus= image and is
already tracked on the LAIF container recipes repo. Drop this container once the
maintainers ship a base image that builds a fused-attention backend.

* Why this container exists

Out of the box the =plus= image runs every attention call through
=UnfusedDotProductAttention= — the vanilla implementation, which materializes the
full =batch x heads x seq x seq= score matrix and OOMs at real sequence lengths.
Two independent causes stack up:

1. LAIF builds the image's TransformerEngine (=ROCm/TransformerEngine= tag
   =v2.8_rocm=) with =NVTE_FUSED_ATTN=0=, so no fused-attention backend is
   compiled in — neither Composable Kernel nor AOTriton.
2. The base ships flash-attn =2.8.4= while TE =v2.8_rocm= hardcodes
   =max_version = PkgVersion("2.8.3")= in =FlashAttentionUtils=. The bound is
   enforced at *import* time in =backends.py=, so =is_installed= stays =False= and
   =flash_attn_func= / =_flash_attn_fwd= are left as =None=. No environment
   variable can recover the backend, because the symbols never exist.

TE's priority is FusedAttention → FlashAttention → UnfusedDotProductAttention, so
with the first two gone every call lands on the third. TE logs the version
mismatch at warning level, but the resulting backend choice only appears at
=NVTE_DEBUG_LEVEL=2= — in practice this surfaces as an unexplained OOM.

Flash attention is installed and fully compiled: LAIF builds it with
=BUILD_TARGET=rocm GPU_ARCHS=gfx90a= and does /not/ set
=FLASH_ATTENTION_TRITON_AMD_ENABLE=, so the =flash_attn_2_cuda= composable-kernel
extension exists and simply sits unused. This container raises TE's cap to unlock
it — one rewritten line, nothing installed, nothing compiled. Do /not/ set
=FLASH_ATTENTION_TRITON_AMD_ENABLE=TRUE=, which would switch flash-attn to a
Triton backend the image never built.

=2.8.4= is a ROCm-fork-only version number; upstream flash-attn 2 stops at =2.8.3=,
so TE's cap records "newest upstream tested", not a known defect.

* Build

#+BEGIN_SRC bash
export PROJECT=<your-project>
export SIF=/scratch/$PROJECT/$USER/transformer-engine-lumi.sif

srun --account=$PROJECT --partition=small --ntasks=1 --cpus-per-task=8 --mem=16G --time=00:30:00 --nodes=1 --pty bash
#+END_SRC

#+BEGIN_SRC bash
module purge
module load CrayEnv
module load PRoot

mkdir -p /tmp/$USER
export SINGULARITY_TMPDIR=/tmp/$USER
export SINGULARITY_CACHEDIR=/tmp/$USER

singularity build $SIF transformer-engine-lumi.def
#+END_SRC

Run the =srun= from a login node — nesting it inside an existing allocation fails
with =Memory required by task is not available=. Nothing is compiled, so this
needs far less than the 120 G/2 h the other guides in this repo ask for.

Pass =--build-arg LAIF_BASE=...= to build on a different LAIF release. The
=%post= patch asserts it found exactly one =max_version= site, so a base-image
bump fails the build loudly rather than silently shipping unfused attention.

The patch derives the new cap from =importlib.metadata.version("flash_attn")=
rather than a literal =2.8.4=. LAIF retags the wheel with
=wretag -q lumi_aif_<arch>_<commit>=, and under PEP 440
=2.8.4+lumi.aif.gfx90a.bbe25ba > 2.8.4=, so a literal bound would still reject the
package — the patch would appear to apply and change nothing.

* Verify

#+BEGIN_SRC bash
singularity test $SIF
#+END_SRC

CPU-side: the ROCm torch build survived, TE now accepts the installed flash-attn,
and TE bound the flash-attn entry points. On a GPU node:

#+BEGIN_SRC bash
srun --account=$PROJECT --partition=dev-g --ntasks=1 --cpus-per-task=8 --gpus=1 --mem=60G --time=01:00:00 --nodes=1 --pty bash
module use /appl/local/laifs/modules
module load lumi-aif-singularity-bindings

singularity exec $SIF python3 /opt/transformer-engine-smoke.py --gpu
#+END_SRC

This runs =DotProductAttention= twice, once with =NVTE_FLASH_ATTN=0=, and asserts
the default run selects FlashAttention, uses less memory, and matches the unfused
reference numerically. Verified on MI250X with torch =2.10.0+rocm7.0=, TE
=2.8.0+a365f2de= and flash-attn =2.8.4+lumi_aif_gfx90a_bbe25ba=: all three pass.

To inspect the stock image instead, bind the script in and add =--bench=; the
version checks fail by design and the sweep still runs. Use
=/opt/venv/bin/python3= if =python3= resolves outside the venv.

* Benchmark

#+BEGIN_SRC bash
singularity exec $SIF python3 /opt/transformer-engine-smoke.py --bench
singularity exec $SIF env NVTE_FLASH_ATTN=0 \
    python3 /opt/transformer-engine-smoke.py --bench
#+END_SRC

One MI250X GCD, =batch=2 heads=16 head_dim=64=, bf16, forward plus backward:

| seq_len | FlashAttention MiB | Unfused MiB | FlashAttention ms | Unfused ms |
|---------+--------------------+-------------+-------------------+------------|
|    1024 |                 40 |         313 |              0.71 |       1.50 |
|    2048 |                 81 |         732 |              2.03 |       4.78 |
|    4096 |                161 |        2344 |              7.46 |      25.38 |
|    8192 |                322 |        8664 |             27.57 |     129.71 |
|   16384 |                644 | OOM         |            108.52 | —          |
|   32768 |               1288 | OOM         |            426.24 | —          |

FlashAttention memory doubles with =seq_len= — linear, and fully accounted for by
q/k/v, their gradients and the output. Unfused converges on 4x per doubling
because of the score matrix, exhausting the 64 GB GCD by =seq_len=16384=. Step
time grows ~3.9x per doubling either way: attention is O(seq^2) in FLOPs, and
flash attention removes the memory traffic, not the work.

* Run workloads

#+BEGIN_SRC bash
singularity exec $SIF python3 /path/to/your_script.py
#+END_SRC

Set =NVTE_DEBUG=1 NVTE_DEBUG_LEVEL=2= whenever an attention regression is
suspected — it is the only way TE reports which backend it chose.
