#+TITLE: Extending Containers on LUMI - SGLang
#+AUTHOR: Anis Rahman
#+OPTIONS: toc:nil
#+OPTIONS: num:nil

An [[https://github.com/sgl-project/sglang][SGLang]] inference server on LUMI-G, in a container extending the LUMI AI
Factory multi-framework image. SGLang does not officially support MI250x - its
ROCm targets are MI300X (=gfx942=) and MI350X (=gfx950=) - so =sglang-lumi.def=
patches it at build time.

Verified 2026-09-22: SGLang =v0.5.6.post2= serving =Llama-3.1-8B-Instruct= on one
MI250x GCD, torch =2.10.0+rocm7.0=, transformers =4.57.1=. Ready in 75 s from
cold, =/v1/chat/completions= returns HTTP 200. See =* Benchmark= below for
throughput against vLLM.

The base is pinned so the same definition always yields the same ROCm stack:

#+BEGIN_SRC text
/appl/local/laifs/containers/lumi-multitorch-u24r70f21m50t210-20260807_115122/lumi-multitorch-full-u24r70f21m50t210-20260807_115122.sif
#+END_SRC

The pin is one line in =%arguments=; override it with
=--build-arg LAIF_BASE=/path/to/base.sif=.

* What the container patches

- *=pyproject_other.toml= instead of =pyproject.toml=.* The default pulls
  CUDA-only deps (flashinfer, sgl-kernel, nvidia-cutlass-dsl) and =aiter=, whose
  =composable_kernel= build needs FP8 kernels gfx90a lacks ([[https://github.com/ROCm/aiter/issues/179][ROCm/aiter#179]]). The
  AMD variant drops all of them.
- *=sgl_kernel= and =aiter= stubs.* SGLang imports both at module level even
  though the calls are guarded by =is_hip()=. A =MetaPathFinder= satisfies the
  imports at any depth.
- *=forward_hip= redirected to =forward_native=.* An AST sweep rewrites every
  =forward_hip= reaching =sgl_kernel=, =aiter=, =forward_cuda=, or the 6-argument
  =fused_add_rms_norm= the base's vLLM rejects. Slower, but correct.
- *The venv prepended to =PYTHONPATH=.* The base sets
  =PYTHONPATH=/opt/venv/lib/python3.12/site-packages=, which outranks a venv's own
  =site-packages= and shadows everything SGLang pinned. Transformers then
  resolves to the base's 5.10.1 instead of 4.57.1 and =/v1/chat/completions=
  returns =400 input_ids should be a list of lists=, while the server still
  starts and =/generate= still works. Prepend rather than unset - torch comes
  from the base. =singularity test= asserts this, so the next base bump fails
  the build instead of the first request.
- *=get_amdgpu_memory_capacity= fallback.* SGLang parses =rocminfo= output that
  does not match on gfx90a; the =ValueError= escapes its =except
  FileNotFoundError=. Falls back to =torch.cuda.mem_get_info()=, as the NVIDIA
  path already does.

Two flags follow from this: =--attention-backend triton= (no FlashInfer on
gfx90a) and =--disable-cuda-graph= (capture trips kernel checks on gfx90a).

* Build

#+BEGIN_SRC bash
export PROJECT=<your-project>
export SIF=/scratch/$PROJECT/$USER/containers/sglang-lumi.sif
#+END_SRC

#+BEGIN_SRC bash
srun --account=$PROJECT --partition=small --ntasks=1 --cpus-per-task=8 --mem=120G --time=01:00:00 --nodes=1 --pty bash
#+END_SRC

#+BEGIN_SRC bash
module purge
module load CrayEnv
module load PRoot

mkdir -p /tmp/$USER $(dirname $SIF)
export SINGULARITY_TMPDIR=/tmp/$USER
export SINGULARITY_CACHEDIR=/tmp/$USER

singularity build $SIF sglang-lumi.def
singularity test $SIF
#+END_SRC

About 7 minutes. =%post= clones and pip-installs, which works from =small=
compute nodes.

* Get a model

#+BEGIN_SRC bash
module purge
module use /appl/local/laifs/modules
module load lumi-aif-singularity-bindings

export MODEL=/scratch/$PROJECT/$USER/models/Llama-3.1-8B-Instruct
mkdir -p $MODEL

singularity exec $SIF hf download meta-llama/Llama-3.1-8B-Instruct \
    --local-dir $MODEL --token $HF_TOKEN
#+END_SRC

=HF_TOKEN= needs access to the gated repo:
[[https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct]].

* Run

SGLang reads GPU memory while parsing arguments, so it needs a GPU allocation -
without =--gpus-per-node= it exits immediately. Seven cores per GCD is the LUMI-G
ratio.

#+BEGIN_SRC bash
srun --account=$PROJECT --partition=dev-g --nodes=1 --ntasks=1 --cpus-per-task=7 --gpus-per-node=1 --mem=120G --time=01:00:00 --pty bash
#+END_SRC

#+BEGIN_SRC bash
module purge
module use /appl/local/laifs/modules
module load lumi-aif-singularity-bindings

singularity exec ${HF_TOKEN:+--env HF_TOKEN=$HF_TOKEN} "$SIF" \
    python -m sglang.launch_server \
        --model-path "$MODEL" \
        --host 0.0.0.0 \
        --port 30000 \
        --tp-size 1 \
        --attention-backend triton \
        --disable-cuda-graph
#+END_SRC

Set =--tp-size= to the number of GCDs allocated. For a batch job see
=scripts/sglang-serve.sh=.

Use the bindings module, not =singularity exec --rocm=: =--rocm= injects the
host's ROCm userspace and fails with =ImportError: GLIBC_2.33 not found=, and
the image already ships its own ROCm stack.

* Test

The server holds the terminal and compute nodes refuse direct SSH, so attach a
second shell to the job from a login node. Note that =--overlap= shells inherit
nothing, so re-export =MODEL= and reload the bindings module there.

#+BEGIN_SRC bash
squeue --me
srun --overlap --pty --jobid=<JOBID> bash
#+END_SRC

#+BEGIN_SRC bash
curl -s http://localhost:30000/health

curl -s http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "default",
       "messages": [{"role": "user", "content": "What is 2+2?"}],
       "max_tokens": 50}' | python3 -m json.tool
#+END_SRC

The reply is in =choices[0].message.content=.

* Benchmark

One MI250x GCD, Llama-3.1-8B-Instruct, 1024 in / 256 out, 40-600 prompts scaled
with concurrency, median of 3-6 runs:

| concurrency | SGLang tok/s | SGLang ITL ms | vLLM tok/s | vLLM ITL ms | vLLM eager tok/s |
|-------------+--------------+---------------+------------+-------------+------------------|
|           1 |           28 |          35.1 |         72 |        13.7 |               63 |
|           8 |          197 |          34.8 |        327 |        20.1 |              293 |
|          32 |          589 |          36.4 |        816 |        26.0 |              810 |
|          64 |          764 |          42.2 |        917 |        34.8 |              911 |

vLLM is faster at every level, but its lead falls from 2.6x at concurrency 1 to
1.2x at 64. SGLang's inter-token latency barely moves across the sweep (35 to 42
ms) while vLLM's climbs from 13.7 to 34.8, so the two converge under load; by
concurrency 64 SGLang has the better time to first token (234 ms against 272
ms). Both engines completed every request at every level, with identical output
token counts.

The =vLLM eager= column runs vLLM with =--enforce-eager=, which disables the
CUDA graphs SGLang cannot use on gfx90a. It costs vLLM 12% at concurrency 1 and
nothing measurable at 32 and above, so graphs are not what separates the two
engines under load - the kernels are. vLLM here is =0.22.1+lumi.aif.gfx90a=,
built for this architecture, against SGLang running the pure-PyTorch
=forward_native= fallbacks described above. The gap is the cost of that
fallback, not a property of SGLang itself.

Tensor parallelism across all eight GCDs of a node, same workload:

| concurrency | SGLang tok/s | SGLang ITL ms | vLLM tok/s | vLLM ITL ms |
|-------------+--------------+---------------+------------+-------------|
|           1 |           21 |          46.7 |        176 |         5.5 |
|           8 |          153 |          46.8 |        737 |         9.1 |
|          32 |          534 |          48.1 |       1772 |        12.9 |
|          64 |          929 |          48.4 |       3169 |        16.7 |

This reverses the single-GCD picture. vLLM gains 2.2x to 3.5x from the extra
seven GCDs, while SGLang is *slower* on eight GCDs than on one at every
concurrency below 64 (0.75x at 1, 0.91x at 32) and manages only 1.22x at 64.
Its inter-token latency gets worse with more hardware, 36 ms to 48 ms, where
vLLM's improves from 26 ms to 13 ms. So vLLM's lead widens from 1.2x to 3.4x at
concurrency 64 rather than narrowing.

Neither engine scales anywhere near linearly, which is expected: an 8B model
fits in one 64 GB GCD, so sharding it adds an all-reduce per layer and buys no
memory headroom. Scaling efficiency against 8x the hardware is 27-43% for vLLM
and 9-15% for SGLang. The practical consequence is that tensor parallelism is
not a way to make this SGLang container faster on MI250x - for a model this
size, run tp=1 and add replicas. Reserve tp>1 for models that do not fit in a
single GCD, and re-measure if you go that way.

Reproduce with =scripts/bench-sglang.sh= and =scripts/bench-vllm.sh= (set =TP=8=
for the multi-GCD table with a matching =--gpus-per-node=8=, and
=EAGER=1= for the third column), then =scripts/bench-report.py <bench-dir>= to
regenerate this table. Both engines are driven through =/v1/completions= by the
same =sglang.bench_serving= client, so neither is measured by its own tooling.
Run the sweep more than once: a single run is not stable enough to quote, and
short runs overstate throughput badly.
