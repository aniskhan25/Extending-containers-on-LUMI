Examples of extending the LUMI AI Factory (LAIF) PyTorch Singularity container
with additional Python packages.

| Container definition | Purpose                                        |
|----------------------+------------------------------------------------|
| =sglang-lumi.def=    | SGLang inference server (MI250x, experimental) |

* SGLang on LUMI (Experimental)

** Status and Caveats

Confirmed working on MI250x (=gfx90a=/CDNA2) with SGLang v0.5.6.post2 and
Llama-3.1-8B-Instruct.  SGLang does *not* officially support MI250x — the
official ROCm targets are MI300X (=gfx942=) and MI350X (=gfx950=) — so the
container applies several compatibility patches at build time.

Known limitations on MI250x:

1. *=aiter= not compatible with gfx90a* ([[https://github.com/ROCm/aiter/issues/179][ROCm/aiter#179]]): the default
   =pyproject.toml= pulls in =aiter=, whose =composable_kernel= build includes
   FP8 kernels that gfx90a does not support, causing a build failure.
   SGLang ships =pyproject_other.toml= as the AMD variant, which removes
   =aiter= (and all other CUDA/NVIDIA-only deps) entirely.

2. *No FlashInfer on MI250x*: FlashInfer's ROCm builds cover MI300X/MI325X/
   MI355X only.  The Triton attention backend is used instead
   (=SGLANG_ATTENTION_BACKEND=triton=, set automatically by the container).

3. *CUDA graphs disabled*: =--disable-cuda-graph= is required; CUDA graph
   capture triggers kernel compatibility checks that fail on gfx90a.

4. *Pure-PyTorch kernel fallback*: the container patches all =forward_hip=
   methods that reference =sgl_kernel= or incompatible vLLM ops to use
   =forward_native= (pure PyTorch).  This is correct but slower than the
   compiled kernels available on MI300X.

5. *GPU allocation required at runtime*: SGLang queries GPU memory during
   argument parsing.  Always run inside a GPU allocation — without
   =--gpus-per-node= the server crashes immediately.

Expect reduced throughput compared to MI300X.  Suitable for development and
testing; evaluate performance before production use.

** Step 1 — Build the image

Get an interactive CPU node (no GPU needed for the build):

#+BEGIN_SRC bash
srun --account=$PROJECT --partition=small \
     --ntasks=1 --cpus-per-task=8 --mem=120G \
     --time=02:00:00 --nodes=1 --pty bash
#+END_SRC

Set up the build environment:

#+BEGIN_SRC bash
module purge
module load CrayEnv
module load PRoot

mkdir -p /tmp/$USER
export SINGULARITY_TMPDIR=/tmp/$USER
export SINGULARITY_CACHEDIR=/tmp/$USER
#+END_SRC

Build the image:

#+BEGIN_SRC bash
export LAIF_BASE=/appl/local/laifs/containers/lumi-multitorch-latest.sif
export SIF=/scratch/$PROJECT/$USER/lumi-sglang.sif

singularity build --build-arg LAIF_BASE=$LAIF_BASE $SIF sglang-lumi.def
#+END_SRC

** Step 2 — Download a model

Do this once from a login node or CPU allocation — no GPU needed.

#+BEGIN_SRC bash
module purge
module use /appl/local/laifs/modules
module load lumi-aif-singularity-bindings
#+END_SRC

#+BEGIN_SRC bash
export SIF=/scratch/$PROJECT/$USER/lumi-sglang.sif
export MODEL_DIR=/scratch/$PROJECT/$USER/models/Llama-3.1-8B-Instruct

mkdir -p $MODEL_DIR

singularity exec $SIF \
  hf download meta-llama/Llama-3.1-8B-Instruct \
  --local-dir $MODEL_DIR \
  --token $HF_TOKEN
#+END_SRC

=HF_TOKEN= must have access to the gated model.  Request access at
[[https://huggingface.co/meta-llama/Llama-3.1-8B-Instruct]] if needed.

** Step 3 — Get a GPU allocation (dev-g)

#+BEGIN_SRC bash
srun --account=$PROJECT --partition=dev-g \
     --nodes=1 --ntasks=1 --cpus-per-task=7 \
     --gpus-per-node=1 --mem=120G \
     --time=01:00:00 --pty bash
#+END_SRC

Adjust =--gpus-per-node= and =--cpus-per-task= for multi-GPU runs
(7 CPU cores per GPU is the recommended ratio on LUMI-G).

** Step 4 — Set up the runtime environment

#+BEGIN_SRC bash
module purge
module use /appl/local/laifs/modules
module load lumi-aif-singularity-bindings

MIOPEN_DIR=$(mktemp -d)
export MIOPEN_CUSTOM_CACHE_DIR=$MIOPEN_DIR/cache
export MIOPEN_USER_DB=$MIOPEN_DIR/config
#+END_SRC

** Step 5 — Run the server

#+BEGIN_SRC bash
export SIF=/scratch/$PROJECT/$USER/lumi-sglang.sif
export MODEL=/scratch/$PROJECT/$USER/models/Llama-3.1-8B-Instruct

singularity exec \
  ${HF_TOKEN:+--env HF_TOKEN=$HF_TOKEN} \
  "$SIF" \
  python -m sglang.launch_server \
    --model-path "$MODEL" \
    --host 0.0.0.0 \
    --port 30000 \
    --tp-size 1 \
    --attention-backend triton \
    --disable-cuda-graph
#+END_SRC

Set =--tp-size= to match the number of GPUs allocated.  Use a local model
path under =/scratch= or a HuggingFace model id (requires =HF_TOKEN= for
gated models).

For a SLURM batch job see =scripts/sglang-serve.sh=.

** Step 6 — Test the server

The server runs in the foreground.  LUMI compute nodes do not accept direct
SSH, so use =srun --overlap= to attach a second shell to the same job.
From a *new terminal* logged into any LUMI login node:

#+BEGIN_SRC bash
squeue --me              # note your JOBID
srun --overlap --pty --jobid=<JOBID> bash
#+END_SRC

Then test:

#+BEGIN_SRC bash
# Health check
curl -s http://localhost:30000/health

# OpenAI-compatible chat request
curl -s http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "default",
    "messages": [{"role": "user", "content": "What is 2+2?"}],
    "max_tokens": 50
  }' | python3 -m json.tool
#+END_SRC

You should see a JSON response with the reply in =choices[0].message.content=.

To run the server in the background instead (frees the terminal):

#+BEGIN_SRC bash
singularity exec \
  ${HF_TOKEN:+--env HF_TOKEN=$HF_TOKEN} \
  "$SIF" \
  python -m sglang.launch_server \
    --model-path "$MODEL" \
    --host 0.0.0.0 \
    --port 30000 \
    --tp-size 1 \
    --attention-backend triton \
    --disable-cuda-graph \
  > sglang.log 2>&1 &

echo "Server PID: $!"
tail -f sglang.log   # watch startup; Ctrl-C once you see "ready to roll"
#+END_SRC
